# Guideline 19: Pseudo-Random Numbers with Python

Computers are, at their core, deterministic — the same instructions given the same input will always produce the same output. So where does "randomness" in a program actually come from? The honest answer is that it doesn't, not really. What Python (and virtually every programming language) provides is **pseudo-random** numbers: values generated by an algorithm that *looks* statistically random and passes for unpredictable in practice, but is technically the deterministic output of a formula, starting from some initial number called a **seed**. Given the same seed, the exact same "random" sequence comes out every time. This isn't a flaw — it's actually a feature you'll rely on later in this guideline.

All of this lives in the standard library's **`random` module**.

### Importing

```python
import random
```

Or, to skip the `random.` prefix and import only the specific tools you need:

```python
from random import choice, randint, uniform, shuffle
```

The rest of this guideline is a working reference table for the functions you'll use constantly, followed by a closer look at the handful that deserve more explanation than a single table row can give.

---

## Reference Table: The `random` Module

| Function | Description | Example |
|---|---|---|
| `random.random()` | A random float, `0.0 <= x < 1.0` | `random.random()` → `0.6741...` |
| `random.randint(a, b)` | A random integer, **inclusive** on both ends: `a <= x <= b` | `random.randint(1, 6)` → `4` |
| `random.randrange(start, stop, step)` | A random integer chosen the same way `range()` would generate one — `stop` is **excluded** | `random.randrange(0, 10, 2)` → `6` (only even numbers 0–8 possible) |
| `random.uniform(a, b)` | A random float between `a` and `b` (inclusive of both ends, unlike `randrange`) | `random.uniform(1.5, 4.5)` → `2.973...` |
| `random.choice(sequence)` | One random element picked from a non-empty sequence | `random.choice(["rock", "paper", "scissors"])` → `'paper'` |
| `random.choices(population, weights=None, k=1)` | A list of `k` elements picked **with replacement** — the same item can be picked more than once | `random.choices(["A", "B", "C"], k=5)` → `['B', 'A', 'A', 'C', 'B']` |
| `random.sample(population, k)` | A list of `k` **unique** elements, picked **without replacement** | `random.sample(range(1, 50), 6)` → `[3, 17, 22, 8, 41, 12]` |
| `random.shuffle(sequence)` | Shuffles a mutable sequence **in place** — returns `None`, modifies the original | `random.shuffle(my_list)` → `my_list` is now reordered |
| `random.seed(value)` | Initializes the generator to a fixed starting state, making results reproducible | `random.seed(42)` |

## A Closer Look

### `choice()` vs. `choices()` vs. `sample()`

These three are the most commonly confused functions in the module, because they all "pick from a group" — the difference is entirely in *how many* and *whether repeats are allowed*.

```python
deck = ["A", "K", "Q", "J", "10"]

random.choice(deck)              # one single item, e.g. 'Q'
random.choices(deck, k=3)        # 3 items, WITH replacement — repeats possible
random.sample(deck, 3)           # 3 items, WITHOUT replacement — always unique
```

`choices()` also supports a `weights` argument, letting some options be more likely than others — useful for anything from a loot table to a weighted survey simulation:

```python
outcomes = ["common", "rare", "legendary"]
random.choices(outcomes, weights=[80, 15, 5], k=10)
# ['common', 'common', 'rare', 'common', 'common', 'legendary', ...]
```

`sample()`, by contrast, is the right tool whenever "the same item twice" would be wrong — dealing unique cards from a deck, picking distinct raffle winners, or selecting a subset of unique participants from a list.

### `randint()` vs. `randrange()`

Both return an integer, but their boundaries behave differently — `randint(a, b)` includes `b`, while `randrange(start, stop)` excludes `stop`, exactly like the built-in `range()` does.

```python
random.randint(1, 10)     # can return 10
random.randrange(1, 10)   # can never return 10, only up to 9
```

`randrange()` also accepts a `step`, letting you restrict results to a pattern — every other number, every fifth number, and so on — which `randint()` cannot do at all.

### `shuffle()`

Unlike every function above it, `shuffle()` doesn't return a new value — it rearranges the sequence you give it **in place** and returns `None`. This means it only works on a mutable sequence (a list), not a tuple or a string.

```python
cards = ["A", "K", "Q", "J", "10"]
random.shuffle(cards)
print(cards)  # ['J', 'A', '10', 'Q', 'K']  -> same list, reordered
```

If you want a *shuffled copy* while leaving the original untouched, `random.sample(cards, len(cards))` accomplishes that instead, since `sample()` always returns a new list.

### `seed()`

This is the one function in the table that doesn't generate a random value itself — it controls the *starting state* of every function that comes after it. Calling `random.seed()` with the same value guarantees the exact same sequence of "random" results, which is invaluable for debugging, testing, and reproducible examples.

```python
random.seed(42)
print(random.randint(1, 100))  # always the same number, every run
print(random.randint(1, 100))  # always the same second number, every run

random.seed(42)  # reset back to the same starting state
print(random.randint(1, 100))  # identical to the very first call above
```

Without a fixed seed, Python quietly seeds the generator from a source like the system clock, which is why two runs of the same program normally produce different results — and why `seed()` is the one thing standing between "random" and "reproducibly random," a distinction that matters a great deal once you start writing tests or trying to reliably demonstrate a bug.

---

Pseudo-randomness might sound like a compromise, but for almost every practical purpose — games, simulations, sampling, shuffling — it's indistinguishable from the real thing, and it comes with a genuine advantage true randomness doesn't: the ability to pin it down with `seed()` whenever reproducibility matters more than surprise.
